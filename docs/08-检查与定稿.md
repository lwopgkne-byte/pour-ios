# 08 检查与定稿

> 按产品主人要求的顺序做：理顺需求 → 写成提示词 → **检查提示词** → 输出方案 → **检查方案** → 定稿。本文记录每一轮检查查出了什么、怎么改的。v1.0 是第一轮；v1.1 是按产品主人第二轮意见的修订和复查。

---

## 1. 第一轮：提示词检查

### 1.1 产品主人的每一句话，在提示词里落到了哪

| 原话要点 | 提示词 |
|---|---|
| 网页版只是 DEMO、个人用还行 | 第 2 节「它的局限」 |
| 商用、上架 App Store、每个人都能用 | 第 0、3 节 |
| 功能基本都做了，UI 和操作细节还有很多要提升 | 第 8 节视觉要求 + **交互和操作细节要求**（检查后补） |
| 你对项目很了解，因为是你做的 | 第 1 节 |
| 参考复刻现在的项目，用 iOS 做出来 | 第 5、7 节 |
| 高水准、商业级，前期几百人、以后几十万 | 第 3 节（含「能长大」，检查后补） |
| 交互、流畅度、性能一定要最好 | 第 3、4 节 |
| 按模块做，一个模块验收一个；你先验收，没问题了我再验收 | 第 6 节 |
| 不能比现在差：AI 能力、测试能力、准确率、性能 | 第 4 节（每条带「怎么证明」） |
| 吸取最有价值的、灵活选最合适的、不照抄，两个项目差距大 | 第 5 节 |
| 全方位、系统、完整 | 第 7 节（八份交付物） |
| 开发、设计、演示、测试、AI 能力和程序适配方案 | 第 7 节 |
| 代码管理、上传仓库 | 第 10 节 |
| 在 Mac 上开发，我会在 Mac 上拉取代码和方案 | 第 10 节 |
| 视觉还差点意思、太素；一线 App 的高级感，简约不简单，让人想用 | 第 8 节 |
| 之前参考 Notion，但 Notion 手机端一般 | 第 8 节（检查后补：这次不拿它当样板） |
| 设计三层（宪法、系统、审查），适配安卓和 iOS | 第 8 节 |
| 十个知识来源 | 第 8 节 |
| 可以上网找，选最合适、最好、简约、高级、原创 | 第 8 节 |
| 先理解 → 提示词 → 检查 → 方案 → 检查 → 定稿 | 本文 |

### 1.2 查出来、已经改掉的

| # | 问题 | 改法 |
|---|---|---|
| 1 | 「操作细节」只出现在附录的原话里，没变成要求 | 第 8 节加「交互和操作细节要求」五条（100 毫秒回应、拇指区、撤销优先、全状态、系统能力用足） |
| 2 | 「几十万人」只写在目标里，没落到架构 | 第 3 节加「能长大」：网关横向扩、成本按人封顶、数据在用户设备 |
| 3 | 没说清不再拿 Notion 手机端当样板 | 第 8 节写明 |
| 4 | 「没网也能记」没写成要求（手机上最常见的情况） | 第 3 节补上 |
| 5 | **产品主人网页版里的真实数据要搬进 App——完全漏了** | 第 4 节红线加一行「数据」：一条不丢，逐表对数 |
| 6 | 市场和语言的先后没交代 | 第 3 节：列为待拍板的决定；代码从第一天按可多语言写 |
| 7 | 「15 份 Skill」不准确 | 改为「14 份 Skill 加 1 份共用的语气规则」 |

### 1.3 理解上的两处不确定（如实说明）

- **「Munas」**：没能确认是哪款 App，按「同级别一线 App」处理（设计方案 B16 写明）；告诉我是哪个，我补进对标表
- **「对定价」**：理解为「对标」（向最好的学），同时因为是商用，在总体方案第 8 节补了定价和成本账

## 2. 第一轮：方案检查

### 2.1 怎么查的

1. 每份方案对照提示词第 12 节的核对清单
2. 跨文件核对：模块编号、评测和测试的数字、性能预算、决定编号、引用的文件是否存在
3. **用脚本重算**设计方案里的全部对比度（不靠心算）
4. 逐句看隐私相关的说法有没有说过头
5. 关键事实对照调研来源（见第 4 节）

### 2.2 查出来、已经改掉的

| # | 问题 | 严重 | 改法 |
|---|---|---|---|
| 1 | **九个领域色在亮色模式下对白卡只有 2.4–3.1:1**，没达到图形 3:1 的要求；初稿却写着「≥ 3:1」 | 高 | 亮色模式用同色相加深一档（脚本实算全部 ≥ 3.3:1），亮暗两套分开；写明「同一套颜色亮暗不能共用」（网页版踩过的坑） |
| 2 | 几个对比度数字是心算的，有偏差（如主文字写成 16.9:1，实为 17.6:1） | 中 | 全部按脚本结果改正，分别写「卡上 / 纸上」 |
| 3 | **问答的隐私说过头**：初稿写「数据不出手机」，实际上问题和查出来的那几条要发给模型 | 高 | 改成准确说法：在手机上查，只发回答这个问题用得到的那几条 |
| 4 | 「原话只在你的手机和 iCloud 里」容易被理解成从不离开手机 | 中 | 改为「存在手机和 iCloud；整理时经过服务器，处理完就忘」 |
| 5 | 没有容量估算，「几十万人扛不扛得住」没答 | 中 | AI 方案第 5 节加：10 万日活时高峰约每秒 150 次模型调用；企业额度、备用分流、上线前全链路压测 |
| 6 | 没写多语言怎么做 | 低 | 开发方案加 A19：String Catalog，简体中文为基准 |
| 7 | 合规路线漏了**名字和商标**（App Store 中国区重名、商标被抢注会卡上架）、软著 | 中 | 合规路线加第 0 步（名字和商标）、第 10 步（软著，可选） |
| 8 | 把倾倒栏放进 iOS 26 标签栏「底部附件」写成了定论，但它原本是给迷你播放条设计的，和键盘、中文输入法的配合没验证过 | 中 | 改为「优先用它，M5 真机实测；不好就用自己的浮动栏」 |
| 9 | 定价表把「主题起名」「你的一年的故事」列为 Pro 独有，和设计方案矛盾（你的一年全是程序算的），也违背「只按花钱的东西分档」 | 中 | Pro 只按真正花钱的分档：不限整理、不限问答、每晚自动检查 |
| 10 | ADR 编号范围、README 和本文被引用但还不存在 | 低 | 更新编号；补上 README 和本文 |

### 2.3 核对通过的

- 模块编号 M0–M16 在总体方案、开发方案、测试方案里一致
- 网页版的数字（评测 340 / 13 / 28 / 问答 48，全量 99.93%；单元 1,095；页面 47 个场景 107 次运行；演示检查 74 项）各处一致，都来自仓库实测
- 性能预算在开发方案、测试方案里一致；基准机都是 iPhone 13
- 定价的算术（年付月均到手约 ¥9.4、各类用户成本）核对无误
- 合规和平台事实都有来源（第 4 节）

## 3. 第二轮：产品主人的意见（v1.1）

### 3.1 意见和改法

| 意见 | 改了什么 |
|---|---|
| 那些决定先不用管；先不管定价，**先把产品做好** | 总体方案的决定分成三组：技术决定（架构师定）、**以后再定**（市场、主体、定价、合规——写清什么时候必须定、为什么现在可以等）、待你看（D10）；定价表和合规路线从主线里拿掉；模块路线到 M16 内测为止，上架排在商业决定之后 |
| 对标的是 **Manus** | 查了 Manus 的设计：单色、浅灰白底、白卡片、深炭灰点缀，靠层级和留白出高级感。加进对标表，并且**改了视觉方案的核心**：操作（按钮、链接、选中）全部改用墨色，品牌色「青」只表示「它懂你」 |
| 「素」是**全方位的规范**：高亮、字体、颜色、UI 样式等等 | 设计系统从设计方案里独立出来，写成 **12 份完整规范**（`设计规范/`）：颜色（原始色板 + 语义令牌，亮暗两套，全部按 OKLCH 生成、对比度脚本实测）、字体（三种声音、11–56 的阶梯、中文排版）、**高亮与强调**（五级强调、八种高亮）、图标、布局、形状和材质、动效和触感、**组件**（每个组件的尺寸、状态、行为、无障碍）、数据可视化（13 种图）、文案、深色和无障碍、交互和页面 |
| **之前的用户数据不要管了**，从来没有人真正用过 | 删掉所有「搬家 / 迁移」：提示词的红线、M13、测试方案、代码管理里都去掉；网页版只作为规则对拍的参照 |
| 做 iOS App，**架构要重新设计**：能用的就用，不能用的想办法 | 开发方案重写成「架构与开发方案」：先立 7 条架构原则；**复用地图**逐项写沿用 / 重做 / 不需要和办法；**全新的领域模型**（人和地方是一等公民、钱单独成表、一段话一个改动包、原话位置精确到字、基础类别用数据库约束守住）；关键流程、App 结构、网关结构 |
| D10 待会再看 | 视觉方向标为「待你看」；规范里的值都跟着 D10 走，若要调只改原始色板 |

### 3.2 这一轮查出来、已经改掉的

| # | 问题 | 改法 |
|---|---|---|
| 1 | 心情五档的浅色几档对底色只有 1.1–1.7:1，**「很差」的格子会和「没记」混在一起**（网页版现在也是这样） | 有心情填色、没记画虚线空格；加图例、点开有字；不硬说达到 3:1 |
| 2 | 暗色卡片和底色几乎分不出（`#11100F` 对 `#0C0B0A`） | 暗色卡片改为 `#1A1917`，加 1 点 `line` 描边 |
| 3 | 领域色暗色的对比度是按旧卡片色算的（写了 7.7–8.2:1） | 按新卡片重算：7.1–7.6:1，仍达标，数字改对 |
| 4 | 领域色的浅底只写了「浅 / 深」，没给色值，算不上完整规范 | 补上 18 个色值 |
| 5 | 暗色卡片描边一处写白 8%、一处写白 10% | 统一为 `line`（白 10%） |
| 6 | 架构写「原话永不修改」，但语音常听错字，用户必须能改 | 改为：能改错字，每次改动进原话历史，改完重新整理那段话 |
| 7 | 全文搜索用三字切分，**两个字的词（「跑步」「加班」）搜不到**，而中文里两字词最常见 | 1–2 个字的搜索直接扫描原话（1 万段几毫秒），3 个字以上走索引 |
| 8 | 同心圆角的例子算错（20 − 16 = 4，太小） | 改为内边距 12 → 8，小于 8 一律取 8 |
| 9 | 一年每天一格照搬网页的 53 列长条，手机上要横着滚 | 改成 12 个月的小日历 3 × 4，一屏看完 |
| 10 | 规范、方案之间的链接和令牌名 | 脚本检查：0 个坏链接；规范里用到的颜色令牌全部在「颜色」里有定义 |

## 4. 定稿

**方案 v1.1，2026-10-17。** 技术决定已定（总体方案 3.1）；商业决定以后再定（3.2）；**视觉方向 D10 待产品主人看**（可以等 M1 的真机样张出来再定）。

**下一步**：产品主人说开工 → M0 开工准备（在 Mac 上搭好环境、定 Bundle ID、打通「代码 → 自动构建 → TestFlight → 你的手机」）。

**以后改方案**：产品主人确认的变更写回对应方案和本文的变更记录；提示词只有产品主人能改。
