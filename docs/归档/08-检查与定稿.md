# 08 检查与定稿

> 按产品主人要求的顺序做：理顺需求 → 写成提示词 → **检查提示词** → 输出方案 → **检查方案** → 定稿。本文记录每一轮检查查出了什么、怎么改的。v1.0 是第一轮；v1.1 是按产品主人第二轮意见的修订和复查。

---

## 2. 第一轮：方案检查

### 2.1 怎么查的

1. 每份方案对照提示词第 12 节的核对清单
2. 跨文件核对：模块编号、评测和测试的数字、性能预算、决定编号、引用的文件是否存在
3. **用脚本重算**设计方案里的全部对比度（不靠心算）
4. 逐句看隐私相关的说法有没有说过头
5. 关键事实对照调研来源（见第 4 节）

### 2.2 查出来、已经改掉的

| # | 问题 | 严重 | 改法 |
|---|---|---|---|
| 1 | **九个领域色在亮色模式下对白卡只有 2.4–3.1:1**，没达到图形 3:1 的要求；初稿却写着「≥ 3:1」 | 高 | 亮色模式用同色相加深一档（脚本实算全部 ≥ 3.3:1），亮暗两套分开；写明「同一套颜色亮暗不能共用」（网页版踩过的坑） |
| 2 | 几个对比度数字是心算的，有偏差（如主文字写成 16.9:1，实为 17.6:1） | 中 | 全部按脚本结果改正，分别写「卡上 / 纸上」 |
| 3 | **问答的隐私说过头**：初稿写「数据不出手机」，实际上问题和查出来的那几条要发给模型 | 高 | 改成准确说法：在手机上查，只发回答这个问题用得到的那几条 |
| 4 | 「原话只在你的手机和 iCloud 里」容易被理解成从不离开手机 | 中 | 改为「存在手机和 iCloud；整理时经过服务器，处理完就忘」 |
| 5 | 没有容量估算，「几十万人扛不扛得住」没答 | 中 | AI 方案第 5 节加：10 万日活时高峰约每秒 150 次模型调用；企业额度、备用分流、上线前全链路压测 |
| 6 | 没写多语言怎么做 | 低 | 开发方案加 A19：String Catalog，简体中文为基准 |
| 7 | 合规路线漏了**名字和商标**（App Store 中国区重名、商标被抢注会卡上架）、软著 | 中 | 合规路线加第 0 步（名字和商标）、第 10 步（软著，可选） |
| 8 | 把倾倒栏放进 iOS 26 标签栏「底部附件」写成了定论，但它原本是给迷你播放条设计的，和键盘、中文输入法的配合没验证过 | 中 | 改为「优先用它，M5 真机实测；不好就用自己的浮动栏」 |
| 9 | 定价表把「主题起名」「你的一年的故事」列为 Pro 独有，和设计方案矛盾（你的一年全是程序算的），也违背「只按花钱的东西分档」 | 中 | Pro 只按真正花钱的分档：不限整理、不限问答、每晚自动检查 |
| 10 | ADR 编号范围、README 和本文被引用但还不存在 | 低 | 更新编号；补上 README 和本文 |

### 2.3 核对通过的

- 模块编号 M0–M16 在总体方案、开发方案、测试方案里一致
- 网页版的数字（评测 340 / 13 / 28 / 问答 48，全量 99.93%；单元 1,095；页面 47 个场景 107 次运行；演示检查 74 项）各处一致，都来自仓库实测
- 性能预算在开发方案、测试方案里一致；基准机都是 iPhone 13
- 定价的算术（年付月均到手约 ¥9.4、各类用户成本）核对无误
- 合规和平台事实都有来源（第 4 节）

## 4. 第三轮：GPT 审计报告的吸收（v1.2）

产品主人用 GPT 扫描了代码，给了一份《Pour 项目整体审计与 App Store／多用户商业化演进方案》（2026-10-16），要求：**优先做出最好用、最美的产品，其它往后排**；吸收报告里有价值的内容。

### 4.1 先看清它的前提

那份报告只看到了网页版的仓库（iOS 方案当时还没推上去），所以它默认的是「**服务器上存所有人的日记**」：大量篇幅在多用户隔离、云数据库、备份演练、跨端框架。我们的架构是「**日记在你的手机和你自己的 iCloud，服务器不存内容**」，它的很多担心在结构上就不存在了；但有十条确实是我们漏的或该加强的。

### 4.2 采纳的

| # | 报告里的建议 | 我们怎么吸收 | 写在哪 |
|---|---|---|---|
| 1 | 删除要彻底、App 内要有入口（苹果 5.1.1） | 「删除所有数据」：本机、你 iCloud 里的、网关上这台设备的用量记录一起删，先提供导出 | 架构 5.8 |
| 2 | 隐私清单、需要说明原因的系统接口、权限说明 | 从 M0 起就有隐私清单；权限说明用到时才加；每次加依赖复核 | 架构 A20、上架清单 |
| 3 | 身份从验证过的令牌取，不信客户端传的用户编号；越权反向测试 | 网关只认令牌里的设备编号；每个接口都有「拿 A 的令牌动 B」的反向测试 | 架构第 7 节、测试方案 |
| 4 | 几百人不要微服务，模块化单体 + 托管 Postgres，队列等真需要再加 | 网关先只用一个 Postgres（计数也放里面），Redis 等真需要再加 | 架构第 7 节 |
| 5 | 先稳定接口契约，Web 和 App 对后端的理解一致 | 背景包、改动包、技能、问答写成带版本的 JSON Schema，手机和网关两边自动测试 | 架构第 7 节、测试方案 |
| 6 | 数据库迁移前先备份、失败能恢复 | **我们漏了**：用户数据只在他手机上，升级失败就是丢数据。改为升级前整份复制、升级后校验、失败自动换回 | 架构 4.4、测试方案 |
| 7 | 隐私承诺要和技术实现一致，不说「端到端加密」，不对模型服务商的处理作绝对承诺 | **我们说过头了**：「处理完不保存」只对我们自己的服务器成立。改成照实写：服务商的处理按签好的协议写，做不到不训练的服务商不用 | 总体方案第 1 节、AI 方案第 10 节、文案规范 |
| 8 | AI 开发要有保护栏：风险分级、交付附真实命令和结果、没跑过的不写通过、高风险人工批准 | 写进提示词和固定动作；自验收报告加「跑过的命令和真实结果」「安全和隐私影响」「怎么退回」 | 提示词第 6 节、架构第 11 节、测试方案 7.1 |
| 9 | GitHub 主分支保护 | M0 开：CI 没过不能合并、不能强推 | 代码管理第 2 节 |
| 10 | 产品主人之前倾向一次性买断 | 记进「以后再定」：到时按真实 AI 成本算账，「买断 + 每月额度」架构也支持 | 总体方案 3.2 |

### 4.3 不采纳的（和理由）

| 报告里的建议 | 为什么不采纳 |
|---|---|
| 用 Capacitor 或 Expo + React Native 做跨端，SwiftUI 只在「只做苹果」时考虑 | 产品主人的第一优先是**最好用、最美**：Liquid Glass、系统手势、端侧中文语音、小组件、120 帧的手感，只有原生 SwiftUI 能做到最好。报告的理由是复用网页代码、兼顾安卓——这两件现在都排在后面；安卓以后另定，设计规范已经写好了到 Material 3 的对应 |
| 把所有人的日记存到云端 Postgres，按多用户隔离 | 我们的日记在用户自己的手机和 iCloud，服务器不存内容：更私密，也从结构上消除了「串号」的风险；残余的风险（网关的身份和用量）已按第 3 条处理 |
| 对象存储、用户数据的备份恢复演练、RPO/RTO | 服务器上没有用户内容；用户数据的备份由 iCloud 负责，我们做好手机上的升级保护（第 6 条）和导出 |
| 新建十来份文档（多租户、同步协议、隐私数据地图……） | 大部分已经在架构方案和 AI 方案里；只在需要时加：接口契约（M2 交付）、上架和运维手册（上架前） |
| 现在就算一次性买断的经济账 | 产品主人说定价以后再定；架构已经能按设备计量和封顶 |
| 阶段 0 先做一轮只读审计、跑基线 | 网页版是 Claude 做的，结构和数字都实测过（单元 1,095、评测 99.93%……），不需要重新摸底 |
| 账号体系（邮箱验证码等） | 为了「最好用」，**改成不用注册登录**（见 4.4） |

### 4.4 按「最好用、最美第一」做的两处调整

| 调整 | 内容 |
|---|---|
| **路线重排** | 不先花几周做看不见的地基：M0 开工 → M1 设计系统和样张 → **M2 说一句 → 今天（第一条完整体验，真的 AI、真的数据，做到一线水准）**→ M3 说得更顺 → M4 回顾和提醒 → 关于我、钱、目标、搜索、问答 → 系统集成 → 同步和数据、打磨、内测往后排。每个模块自己带着要用的规则，当场对拍。共 14 个模块（M0–M13）；第一条完整体验在第 5–7 周 |
| **不用注册登录** | 打开就能用：网关用设备证明认手机，同步用你自己的 iCloud；没有账号，也就没有账号安全、找回、注销这一整套负担；以后跨平台要账号时，设备和账号关联的位置已经留好 |

### 4.5 这一轮的检查

- 模块编号全部按新路线改过（总体方案、AI 方案、测试方案、设计规范里的引用）
- 「账号」相关的说法全部对齐成「不用注册登录 / 删除所有数据」
- 链接和令牌名用脚本复查

## 5. 第四轮：推送前的系统检查（v1.2.1）
